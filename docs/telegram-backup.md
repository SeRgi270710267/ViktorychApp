# Telegram backup

The backup runs in GitHub Actions. It does not need a bot or an assistant at runtime. `.github/workflows/telegram-backup.yml` runs at 11:17 UTC (`17 11 * * *`) and from **Run workflow**. One run sends at most 300 messages and 4 GB, with about 3 seconds between messages, and it honors Telegram `retry_after` on HTTP 429.

`TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHANNEL_ID` are required. If either is missing, the job prints a skip line and exits 0. `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` are used only when a non-video file is too big for one public document. The local `telegram-bot-api` server then starts with `--local` for that run and stops at the end. It is not started when every pending file fits the public API. Nothing in the log is a secret value.

The manifest is `backup/telegram-manifest.json` in the private R2 bucket (prefer `viktorych-data`). The same rows are mirrored to the D1 table `telegram_files`. The manifest is not committed.

## Create the bot, the channel, and the secrets

1. Open Telegram and talk to [@BotFather](https://t.me/BotFather). Send `/newbot`. Follow the prompts. Copy the token. That value is `TELEGRAM_BOT_TOKEN`.
2. Create a private channel. Add the bot as an administrator. Give it permission to post messages.
3. Get the channel id. Forward a post from the channel to [@username_to_id_bot](https://t.me/username_to_id_bot), or open the channel in Telegram Web (`https://web.telegram.org`) and copy the `-100…` id. That value is `TELEGRAM_CHANNEL_ID`.
4. Open <https://my.telegram.org>, then **API development tools**. Create an application if you do not already have one. Copy `api_id` and `api_hash`. Those values are `TELEGRAM_API_ID` and `TELEGRAM_API_HASH`.
5. Add the four GitHub Actions secrets at <https://github.com/ViktorychGroup/ViktorychApp/settings/secrets/actions/new>. Use these names exactly:
   - `TELEGRAM_BOT_TOKEN`
   - `TELEGRAM_CHANNEL_ID`
   - `TELEGRAM_API_ID`
   - `TELEGRAM_API_HASH`
6. The backup also reads the existing Actions secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. If either is missing, the job prints a skip line and exits 0.
7. Optional Actions secret `TG_BACKUP_KEY`: a passphrase of at least 16 characters. It encrypts account data with `openssl enc -aes-256-cbc -pbkdf2 -iter 100000 -salt`. Those copies are not played in the app and are not deleted from R2. Without the key, account data is not uploaded.
8. Optional Actions variables: `TG_MAX_MB` (default `19`, cap `1950`) is the single-document limit. `TG_DELETE_FROM_R2` defaults to on. Set it to `false` to keep every R2 object. `TG_WORKER_URL` overrides the discovered `viktorych-accounts` workers.dev host used to verify a file before deleting it.

The Worker has its own copy of the bot token. It is not the Actions secret. Pushing `.github/telegram-worker-secret` to `main` runs this in `worker/`, with the Actions secret on stdin and `CLOUDFLARE_API_TOKEN` plus `CLOUDFLARE_ACCOUNT_ID` for Wrangler:

```sh
npx wrangler secret put TELEGRAM_BOT_TOKEN
```

The value is never printed. Until that Worker secret is set, a signed-in `GET /tg/…` returns 503 and the app uses the next source. The token is never sent to the browser.

Pushing `.github/telegram-probe` to `main` runs a check that prints `true` or `false` for each of the four secret names, calls `getMe` and `getChat`, and uploads one tiny text file. It does not print secret values.

## What each file does

A file of at most 19 MB, and at most `TG_MAX_MB`, is one `sendDocument` on `https://api.telegram.org`. The app can load it at `/tg/<key>` after you sign in. The workflow fetches that URL, checks the sha256, and then deletes the R2 object when deletion is on (the default). A file over 19 MB is not served by `/tg/` even if `TG_MAX_MB` is higher, and it is not deleted.

Video and long audio over that limit, except anything under `loop/`, `radio/`, `music/`, or `covers/`, is remuxed with ffmpeg to HLS. Segments are about 4 to 6 seconds and each one is under 19 MB. Codecs are copied. If a segment is still too big, the workflow re-encodes and logs `transcoded`, except a synced social video: that one is segmented with `-c copy` and, if a segment still cannot fit, the item is skipped and not re-encoded. Each segment and the init segment is its own public document. The app plays `/tg/<key>/index.m3u8` with the bundled hls.js. The original R2 object is deleted only after every segment matches. This is what makes a long video fit.

The radio loop stays on R2 and is also copied to Telegram. Every version under `loop/` is mirrored, not only the one named by `loop/current.json`: the playlist, init segment, and media segments, both the FLAC tree and the AAC fallback. They are not re-encoded. Each file must be under 19 MB; a larger segment is logged `skipped_too_big` and stays on R2. The manifest records them under `loop/<version>` and `loop/<version>/aac`. The Worker serves `/tg/loop/<version>/index.m3u8` (and `/tg/loop/<version>/aac/index.m3u8`) and rewrites every segment URI to a `/tg/loop/…` route. Those responses are `public, max-age=31536000, immutable`. The loop is never deleted from R2. `loop/current.json` is the live pointer and is not uploaded. `radio/` audio is copied the same way, as the files already are, and is not deleted. Publishing a loop starts this mirror when the Publish radio loop workflow succeeds. That job allows 2,000 files, enough for the FLAC and AAC trees, and the current version is copied first. The daily backup still stops at 300 files or 4 GB. Run workflow with the loop-only option, or pushing `.github/telegram-loop` to `main`, copies the loops without the rest of the backup. The daily backup mirrors every loop version as well.

ViktorychMusic songs under `music/` are copied as they already are: the playlist, the init file, and the encrypted lossless pieces. Cover images under `covers/` and `music/` are copied too. They are not re-encoded and they are never deleted from R2. The app still plays R2 first and uses `/tg/…` only after that request fails. The AES key is not uploaded. A playlist's `#EXT-X-KEY` URI, a `key.bin` file, a `music/` file ending in `.bin`, and any object whose name contains `token` or `secret` stay on R2. Playback from Telegram still asks R2 for that key.

`loop/current.json` includes `"primary": "r2"` or `"primary": "tg"`. A missing field, or any value other than `tg`, means `r2`. The player reads it each time it refreshes that file, about every three minutes. `r2` plays the R2 playlist. `tg` plays `/tg/loop/<version>/index.m3u8` first. If the playlist or a segment fails — a network error, or an HTTP 4xx or 5xx after one retry — the player continues the same version from the other source at the same position. A failure of that source switches back. The next loop version starts on `primary` again. `LOOP_PRIMARY` in `scripts/radio_loop.py` is the switch, and it is `"tg"`. A publish writes `"primary": "tg"`. Pushing that script also runs `--set-primary`, which writes the field onto the live pointer without encoding. When a publish encodes the same duration and the same segment count, it keeps the current version so playback stays on segments that are already mirrored. A changed loop uploads a new version and the mirror copies it after that publish succeeds. No other player change is required.

The live pointer is `"primary": "tg"`, so every listener uses Telegram first. That is about 6 segments a minute (the loop segments are 10 seconds): 360 Worker requests an hour, 8,640 a day. The Workers free tier of 100,000 requests a day covers about 11 listeners if they stayed on Telegram all day. One or two listeners, including a second tab, stay inside that budget. Playback that has fallen back to R2 does not use it. `workers.dev` still runs the Worker on a cache hit, so the estimate counts every segment. `/tg/loop/` allows 800 requests an hour per IP, enough for one listener and a second tab. Other `/tg` routes stay signed in.

A big file that is not video or audio (a zip, a pdf, a large image, and the rest) is uploaded through the local server in parts of at most 1950 MB. Those parts are a backup. The app cannot play them, because `api.telegram.org` `getFile` only returns files of about 20 MB, and the local server is not running while someone is watching. Restore them with `scripts/telegram_restore.py`. If `TELEGRAM_API_ID` or `TELEGRAM_API_HASH` is missing, the job logs `skipped_too_big` and leaves the object on R2.

Story, avatar, and banner media are copied and can be played through `/tg` after the R2 copy fails. That is `stories/` media, `media/avatars/`, and `media/banners/`. They stay on R2. The stories catalog `stories.json` is live Worker JSON and is not uploaded.

`.github/workflows/media-extract.yml` downloads new public posts for every added account in `feeds.config.json` (cuentas añadidas, добавленные аккаунты), plus the TikTok handle the sync already follows. It runs at minute 17 of every third hour (`17 */3 * * *`) and when that workflow, its script, or `feeds.config.json` is pushed to `main`. Videos use `yt-dlp` with `-f 'bv*+ba/b' --merge-output-format mp4 --remux-video mp4 --write-info-json --write-thumbnail`. That is a remux, not a re-encode. TikTok prefers the top h265 or bytevc1 bitrate over the lower h264 variants, then falls back to `bv*+ba/b`. Photo posts and carousels use `gallery-dl --write-metadata` for the full-size original, not a resized thumbnail. `--download-archive` records finished videos in `archive.txt`, stored in R2 at `backup/media-archive.txt`, so a later run does not download them again. gallery-dl keeps its own sqlite archive at `backup/gallery-archive.sqlite`. A TikTok `catalog.json` is stored beside it, keyed by `user_id` and `sec_uid`. The object keys are `tiktok/<handle>/<id>/video`, `tiktok/<handle>/<id>/poster`, and `tiktok/<handle>/<id>/photo/<n>`. Other platforms use `social/<platform>/<id>/…`. A video over 19 MB becomes HLS segments under 19 MB with `-c copy`. The same keys are what the app already requests on `/tg`, so a post in the feed plays the file that this job stored. YouTube watch pages stay embeds in the player; the original file is only the stored copy. Each saved file is probed with ffprobe, and the manifest keeps width, height, codec, bitrate, duration, and the public stats: views, likes, comments, shares, upload date, and ids. Download URLs are not stored. Public pages only. No cookies, no captcha or WAF bypass, and no viewbots. A 403 or a captcha skips that account and is logged. The run pauses between accounts and stops after a small cap. TikTok LIVE is not recorded and is not relayed. A live recording could later be stored as HLS VOD on Telegram if you ask. That is not built. The daily Telegram backup does not download these originals again.

An R2 object for one of those keys is deleted after the Worker sha256 check, the same as other loadable media. Music, covers, radio, the loop, stories, avatars, and banners are still not deleted. If the sync only stored a CDN URL, there is no R2 object to remove.

These are never uploaded: `owner/` files, `backup/` internals (including the manifest), the live Worker JSON (`feeds.json`, `stories.json`, people, suggestions, status, `feeds.config.json`, `data/music.json`, `live/`, `archive/` JSON, `comments/`, `fallback/`, and the Discord JSON), `loop/current.json`, song AES keys, and any object whose name contains a token or a secret. `TG_BACKUP_KEY` is not set by this job. The user decides whether to add it.

Account data stays out unless that key is set: D1 rows, sessions, history, settings, and the prefixes `accounts/`, `profiles/`, `history/`, `lists/`, `settings/`, `sync/`, `users/`, `d1/`, and the same names in the singular. With the key, the ciphertext is one public document when it is at most 19 MB. It is not served and not deleted. A larger ciphertext is logged `skipped_too_big`.

`scripts/telegram_restore.py --key <r2-key> --out restored` reads the manifest from R2, or from `--manifest`. It downloads each part, checks the sha256, joins archive parts, writes an HLS directory, and decrypts an account copy when `TG_BACKUP_KEY` is set. Parts over 19 MB need the local server already listening on `127.0.0.1:8081`.

## Playback

TikTok media loads from /tg first, in the feed, on the post page, and in Shorts. The order is `/tg/<key>/index.m3u8`, then `/tg/<key>`, then the R2 URL when one exists, then the original TikTok URL, then the cover and Open on TikTok. Other synced media (X, Instagram, Threads, VK, Telegram, and YouTube thumbnails) uses that same order. YouTube watch pages stay embeds. Songs, covers, and `radio/` still try the R2 URL first and use `/tg` only after that request fails. They stay primary on R2. The radio loop starts on the `primary` field of `loop/current.json` (`"primary": "tg"` on the live pointer; a missing field still means `r2`) and uses the other source after that one fails. Images that come from Telegram are fetched with the session and shown as a blob. `/tg/loop/<version>/index.m3u8` does not require a session, because the same audio is already public on `r2.dev`. Every other `/tg` route requires a signed-in session, the same sign-up gate as the rest of the app. A Shorts post, a TikTok post while the audience is owner-only, or any post marked owner-only is still owner-only: a signed-in viewer who is not the owner receives 403. A hidden avatar stays hidden.

`feeds.json` in this repo has 69 posts. The backup plans 95 Telegram objects from those posts: the photos, posters, and videos, 15 YouTube thumbnails, and 15 YouTube original videos. YouTube watch pages stay embeds, so those 15 stored videos do not add a stream request while someone is watching. One signed-in load of that home feed is about 70 Worker requests (every photo, thumbnail, and poster). Playing one stored non-YouTube video adds one request when the file is under 19 MB, or one playlist, one init segment, and about one segment every 5 seconds when it was split with `-c copy`. TikTok is owner-only. The added TikTok account stores at most 8 posts, so only the owner generates those requests: up to 8 videos and their posters, and more only when a video over 19 MB was split. A long YouTube original can be hundreds of copy-only segments, so TikTok is uploaded first and the run still stops at 300 files or 4 GB. The Workers free tier is 100,000 requests a day. Two hundred full loads of this feed are about 14,000 requests, plus the owner's Shorts. That fits. `workers.dev` still runs the Worker on a cache hit, so this counts every load. A signed-in viewer is limited to 1,200 `/tg` requests an hour, which covers the feed and one HLS video.

The Worker calls `getFile` with its own `TELEGRAM_BOT_TOKEN` and streams the file. Repeat views use the Cache API. The `file_path` is cached for at most 50 minutes. A signed-out request is 401. The route is rate limited so a normal viewing session stays inside the Workers free 100,000 requests a day.
